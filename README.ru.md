# claude-memory-lint

Проверка целостности файловой памяти [Claude Code](https://claude.com/claude-code).

[English version](README.md)

## Проблема

Claude Code хранит долговременную память как папку markdown-заметок:

```
~/.claude/projects/<слаг-проекта>/memory/
    MEMORY.md          <- индекс, который грузится в контекст каждую сессию
    some-note.md       <- один факт на файл, связи через [[wikilinks]]
```

Эту папку ничто не проверяет, и она гниёт незаметно.

Заметку слили с другой. Шесть заметок продолжают ссылаться на старое имя. Эти
ссылки теперь ведут в пустоту — и никакой ошибки, никакого предупреждения, ни
одной красной подсветки. Ассистент просто перестаёт видеть эту память. Ты
считаешь, что факт помнится; он не помнится.

Нашёл это в собственном репозитории ассистента: **145 мёртвых целей, 234
вхождения на 505 заметок.** Часть висела мёртвой месяцами. Корень оказался один
— расхождение конвенции: у 128 заметок `name:` был в `kebab-case`, а файл в
`snake_case`, поэтому каждая ссылка, написанная по слагу самой заметки, вела на
имя файла, которого не существует.

Инструмент это находит и чинит однозначную часть.

## Установка

Без зависимостей, только стандартная библиотека, Python 3.8+.

```bash
git clone https://github.com/Smyshnikof/claude-memory-lint
cd claude-memory-lint
python claude_memory_lint.py
```

## Запуск

```bash
python claude_memory_lint.py              # найти папку памяти автоматически
python claude_memory_lint.py PATH         # проверить конкретную папку
python claude_memory_lint.py --all        # проверить все свои проекты
python claude_memory_lint.py --fix        # починить однозначное
python claude_memory_lint.py --json       # машинный вывод, для CI
python claude_memory_lint.py --list       # показать найденные папки памяти
```

Код выхода `0` — чисто, `1` — есть замечания, поэтому инструмент как есть
встаёт в CI или git-хук.

```
✗ ~/.claude/projects/my-project/memory
  505 notes, 3 issues

  broken-link: 2  (2 fixable with --fix)
    project_alpha.md:18  [[project_old_name]] does not exist -> did you mean [[project_new_name]]?
    ref_sources.md:16  [[tone-of-voice]] does not exist -> did you mean [[feedback_tone_of_voice]]?

  orphan: 1
    ref_stray_finding.md  unreachable from MEMORY.md - nothing links here
```

## Что проверяет

| Проверка | Что означает |
|---|---|
| `broken-link` | `[[ссылка]]` ведёт на несуществующую заметку |
| `broken-path` | относительная ссылка `./file.md` ведёт на пропавший файл |
| `orphan` | заметка недостижима из `MEMORY.md` по всему графу связей |
| `name` | во фронтматтере нет `name:` или он не совпадает с именем файла |
| `description` | нет `description:` — механизму отбора нечем ранжировать заметку |
| `duplicate` | две заметки заявляют один и тот же `name:` |

Два решения стоит объяснить.

**Сироты считаются по всему графу, а не по индексу.** Заметка, на которую
ссылается только заметка-хаб, прекрасно находится, и подсчёт покрытия индексов
дал бы сотни ложных сирот. Правильный вопрос — достижимость из `MEMORY.md`:
может ли ассистент вообще сюда дойти.

**`name:` обязан совпадать с именем файла.** Ссылки резолвятся по имени файла.
Если `name:` расходится с файлом, любая ссылка, написанная по слагу самой
заметки, ведёт в пустоту — это и есть главная причина `broken-link`. Заметки-
индексы (`index-*.md`) и корневой индекс освобождены: они несут маршруты, а не
факты.

## Что `--fix` делает и чего не делает

Чинит только однозначное:

- битую ссылку, цель которой совпадает ровно с одной существующей заметкой после
  сворачивания регистра и разделителей (`[[my-note]]` → `[[my_note]]`);
- битую ссылку, которая совпадает с одной заметкой при допущении префикса типа
  (`[[tone-of-voice]]` → `[[feedback_tone_of_voice]]`);
- `name:`, расходящийся с именем файла.

Никогда не выдумывает цель, никогда не выбирает между двумя кандидатами и
никогда не трогает `[[ссылку]]` внутри блока кода — это документация, а не
ссылка. Всё остальное выносится тебе на решение. Твоя память — не место, где
инструмент угадывает.

## Конфиг

Необязательный, в `<memory>/.memory-lint.json`:

```json
{
  "entry": "MEMORY.md",
  "allow_dangling": ["zametka-kotoruyu-eshe-napishu"],
  "ignore": ["scratch_*.md"],
  "index_glob": ["index-*.md"]
}
```

Висячая ссылка — легальный способ пометить *«эту память стоит написать»*.
Такие цели перечисляй в `allow_dangling`, чтобы они перестали попадать в отчёт,
и держи список коротким: каждая строка в нём — долг.

## В CI

```yaml
- run: python claude_memory_lint.py ~/.claude/projects/my-project/memory
```

Или как pre-commit хук, если держишь бэкап памяти в репозитории:

```bash
python claude_memory_lint.py "$MEMORY_DIR" || exit 1
```

## Тесты

```bash
python -m unittest discover -s tests
```

21 тест, каждый собирает временную папку памяти с одним конкретным дефектом —
поэтому падение сразу называет сломавшуюся проверку.
